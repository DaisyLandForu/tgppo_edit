## 5. 新增信息的最小实现

在**执行当前分支动作前**，读取完整开放节点集合的 `(lowerbound, depth)`，含 leaves、children、siblings；检查重复计数。当前正在处理的节点不额外混入开放节点集合。

当前定制接口已有 `getMIPState()`，内部使用 `SCIPgetOpenNodesData` 读取开放节点；可在这一既有 Cython 路径附近添加轻量聚合接口，无须升级 SCIP。现有 Python 层未检索到可直接使用的完整 `getOpenNodes` 封装，因此给接口与重新编译预留时间。不能仅用 `getChildren()` 代表全部开放节点。

- 初版输出为归一化 8×8 计数直方图，并保留节点总数、空集合标记、无穷界比例等少量标量；参数量对照一并考虑。
- 界值先统一到求解器内部目标方向，避免最大化、最小化符号混用；尺度只使用当前可用信息或训练集统计。
- 分箱阈值、裁剪范围及归一化参数仅从训练实例校准；不能利用开发/测试的回报或未来最优搜索状态确定。
- 无穷界、空集合、根节点和退化尺度有明确约定，检查输出有限、计数一致。
- 逐次记录扫描节点数、提取耗时与总回调耗时，报告 p50/p95；训练 CPU 预算包含这些费用。

**接口实现限时 3 小时。** 若超过时间仍无法稳定取得完整集合，冻结可用版本，保留 API 缺口和失败复现。可以用现有可取得的额外统计验证非对称 Critic 接口，但必须改名、缩小结论，不能称为完整联合信息验证。优先从现有 `getMIPState` 的扫描中复用工作，避免一次回调重复遍历多遍。

## 6. 实验协议与数据安排

### 6.1 数据划分与随机种子

从官方 25 个训练实例中固定 20 个训练、5 个开发验证；在今天完成原生基线后，按规模、原生难度及已知问题族做分层，保存明确实例清单。不能根据改进模型的输赢挑选验证集。同一来源的高度相似变体尽量成组划分；实例留出结果不宣称是问题族留出泛化。

66 个官方测试实例本周主实验保留，不用于选择模型、分箱和超参数。若主交付完成且有余量，只能在配置锁定后做一次预先声明的测试评估，并如实报告覆盖范围。

区分三类随机性：

- 训练随机种子：3 个独立运行，例如 11、22、33，控制初始化、采样和更新顺序。
- 求解器/实例排列种子：0、1、2，各组采用同一张实例—种子任务表。
- 离线拟合种子：3 个；同一个预测任务使用相同数据划分和训练步数。

若多种子奖励基线使用实例—种子索引，需修改当前仅按实例名读取的元数据路径；不能悄悄用 seed 0 元数据替代其他种子的基线。若来不及实现，所有组的训练求解器种子统一为 0，3 个训练种子仍保留，清楚说明随机性覆盖的缩减。

### 6.2 固定策略预测实验：先形成稳妥证据

先用 R0 的首个有效训练检查点冻结 Actor，在 25 个实例上各采集两个固定求解器种子的轨迹；所有 Critic 变体使用完全相同的动作、奖励和轨迹。Actor 冻结，不随各 Critic 分别采样。前 20 个实例用于拟合和内部早停，后 5 个只做开发预测评估。

主标签为同一条完整有限时域 episode 的经验折扣回报，使用统一 gamma。不能用各 Critic 自己生成的 GAE return 分别作“真值”。采集片段若不完整，要恢复完整结尾或单列为截断数据，不把未知尾部当 0。若使用多步预测目标，所有变体必须共用同一个冻结的尾部预测器，并标记它只是代理目标。

报告每实例 NMSE/MAE、explained variance、模型间配对差和新增提取耗时；先按实例汇总，再对实例取均值，避免大轨迹实例主导结果。回报归一化仅使用训练数据。公开 transition 数、episode 数及无分支实例数。

操作上不必强求“上万条样本”：先得到覆盖多个实例、包含真实终止的有效轨迹；若样本不足，扩大训练实例的重复求解预算，不能从开发集倒灌训练。离线预测改进只支持“信息有预测价值”，不能据此宣称动作排序或求解加速。

### 6.3 在线 PPO：检验能否转化为收益

主矩阵：`R0 / Rcap / Rjoint × 3 个训练种子`，共 9 个训练运行。

- 单次求解上限 120 秒；每运行最多 50 个训练 episode。
- 每运行初始训练 CPU 上限 2 核时，包含采样、扩展特征和网络更新；离线预训练若用于初始化也必须计入或对所有组一致复用。
- 在 0.5、1、2 核时保存模型；若某运行先达到 50 episode，按全部组都达到的共同预算点比较，不能把某组的更长训练结果混入。
- 同一训练种子的三个组复用 Actor 初值和实例—求解器种子安排；不同组后续状态分布自然允许变化。
- 采样时冻结一个策略版本，按小批 episode 收集后统一更新；批次大小先从 4 起测。每条轨迹保存策略版本，不混入更新前后两个版本的数据。
- 原版脚本按整轮实例收集后更新；若调整为小批更新，该调整要对所有主组一致，并写入与原版的差异。最多 50 episode 不等于 50 次 PPO 更新。
- 记录有效决策数、更新次数、KL、熵、失败率和时间。预算内未获得有效 PPO 更新，属于实验不充分，不能视为方法无效。

主结果使用共同预算的最终检查点，避免以开发集反复挑最好模型。早期预算点只作训练效率曲线；如需择优检查点，预先固定同一规则并对所有组执行。

### 6.4 配对评估与统计

主评估矩阵：`3 组 × 3 训练种子 × 5 开发实例 × 3 求解器种子 = 135 次求解`，另列同协议 relpscost 基线。主表每次 120 秒。不同运行的 CPU 核数、线程数、求解参数和机器负载尽量一致；不同方法按配对任务交错调度。

主评估沿用受控设置：关闭原始启发式、使用已知最优目标值作 cutoff；所有组使用相同的 Actor-only 路径，默认保留上游随机采样动作，以相同种子配对。贪心评估若增加，应另成一张表。

必须记录：原始 solver status、是否完成 cutoff 证明、节点数、求解器时间、端到端墙钟时间、上下界、原始 gap、固定 120 秒范围的 PDI、全部回调耗时、是否发生回退/异常。求解时限之外还需进程级墙钟 watchdog；异常和超时不从结果中删除。

注意三项语义：

1. 已知最优值只作为 cutoff，并不自动代表向求解器提供了可行 incumbent。`infeasible` 只有在已验证的 cutoff 任务语义下才可解释为“无更优解”的证明，不能一律映射成原问题求解成功。
2. 受控协议的 gap/PDI 可能缺少有效 incumbent，先检查其数值是否有限且有区分度。可另算依赖已知参考值的 reference-bound integral，但必须单独命名并公布公式，不能冒充原生 PDI。若原生 PDI 退化，主结论改用完成证明比例、限时证明时间和节点诊断，如实说明 PDI 不支持结论。
3. 默认求解器配置、不提供最优 cutoff 的验证属于另一协议；若时间允许，仅做 R0、Rjoint、原生 relpscost 的补充实验，不能与受控主表混合。

时间统计包含全部任务：报告限时完成比例、PAR-2 或统一超时惩罚的时间汇总，以及已完成任务的条件时间。节点数仅在明确定义的可比集合上解释；超时少访问节点可能只是神经回调更慢。PDI 要固定积分范围，提前真正证明完成后仅在有明确零差距依据时延拓为零。

以实例为统计单位，先汇总该实例的求解器种子，再展示 3 个训练种子的波动；不可把所有运行当成独立实例。仅 5 个开发实例时，以逐实例结果、均值/中位数、实例级配对区间为主，不追求显著性标签。

## 7. 计算预算与运行纪律

下面是求解时限预算或训练硬上限，尚不包含全部调度等待，不能当成承诺完成时间。

| 工作 | 规模 | CPU 预算 |
|---|---|---|
| 原生归一化基线 | 25 实例×3 求解器种子×120 秒 | 求解上界 2.5 核时 |
| 固定策略轨迹 | 25 实例×2 种子×120 秒 | 求解上界约 1.7 核时 |
| 9 个在线训练运行 | 每运行≤50 episode、≤2 核时 | 训练总硬上限 18 核时 |
| 最终开发评估 | 135 次×120 秒 | 求解上界 4.5 核时 |
| 离线拟合、修复验证、桥接及余量 | 按阶段记录 | 预留约 10—15 核时 |

总计划约 37—42 CPU 核时；关键阶段有先后依赖，不能简单除以 CPU 数量得到交付时间。GPU 只在不改变结果语义且迁移已验证时用于批量拟合，不为追求显卡利用率临时重写交互系统。

第一轮最多同时 4 个求解 worker，限制 BLAS/PyTorch 每进程线程；通过 30 分钟吞吐和峰值内存测量，再考虑增加到 6—8 个 worker。候选集合 Transformer 的成本随候选数增长，不能仅根据核心数量开满进程。训练与评估分时运行，避免资源争用污染时间指标。

首轮记录采样时间、单次 PPO 更新时间、候选数分布、轨迹内存/磁盘大小，据此预测余下九组运行能否在周四夜间完成。优先删可选扩展；若需要缩短全部训练预算，统一降为 1 核时，保留组别和 3 个训练种子，并重新标记共同预算。不能只缩短较慢的改进组。

## 10. 周五的文件与汇报内容

建议每次运行使用独立 `runs/日期-组别-训练种子/`，保存 `config.json`、`metrics.csv`、`resource_usage.json`、`checkpoint.pt`、`stdout.log`。配置至少包括源码提交/补丁、依赖版本、数据哈希、cutoff 来源、实例划分、三类种子、时限、奖励版本、计时方式和评估模式。现有启动脚本的默认配置是长实验，不能不带修改直接用于 20/5 划分的短实验。

汇报主体控制为以下六项：

1. **复现状态表：** 环境、数据、训练规模、评估规模、与论文差异；明确上周所述复现与本机实际结果的边界。
2. **方法图：** Actor 沿用原观测，Critic 训练时额外读取联合信息；部署只运行 Actor。
3. **信息价值表：** R0/Rcap/Rjoint/Rmarg 的实例外预测误差与提取成本。
4. **在线求解表：** relpscost、R0/Rcap/Rjoint 的限时完成比例、有效 PDI/证明指标、时间、节点和开销；展示训练种子波动。
5. **三张图：** 按实例配对散点；共同 CPU 预算下性能曲线；特征提取/封装/Actor 推理耗时分解。
6. **判断与下一步：** 只有当信息预测增益和多种子在线收益都支持时，才进入“记忆 Critic → Mamba Actor → 预算化续跑校准”。若证据不支持，给出对应的调整，而非直接堆叠模块。

预先约定推进信号：例如 Rjoint 在多数训练种子上优于 Rcap，且固定预算主求解指标改善约 5% 或以上、没有明显降低完成比例，可视为值得扩大实验的工程信号；这不是统计显著性门槛，更不是必须达到的汇报数字。五个开发实例上的正结果仍需更广泛正式测试确认。

## 11. 原规模复现与后续改进的衔接

周五之后继续完成论文规模复现时，恢复 3600 秒协议及对应原生基线，按论文核对 episode 数、更新频率和 5 个求解器种子；不能把上周/本周的 120 秒回报归一化参数直接带入。采用的正确性修复与上游差异单独公开，评估 66 个官方测试实例，并保留原生强基线。

主假设成立后，按以下依赖推进完整方案：

1. 在同样 Actor 下比较 Critic 有/无策略记忆，先判断记忆信息的独立作用。
2. 接入 Mamba Actor；连续片段重建隐藏状态，实例切换时清零，检查截断与真实终止。
3. 验证完整搜索状态的一致恢复或确定性重放，重复相同动作时对比开放节点、全局割、伪成本、界、随机状态和后续轨迹。未通过一致性检查，不构造“同状态动作比较”结论。
4. 再从 2 个候选、32 步续跑开始，核算恢复/重放/特征/续跑的全部费用；与相同额外 CPU 预算的随机探测比较，先用于价值辅助训练，再考虑经过采样概率处理的优势校准。
