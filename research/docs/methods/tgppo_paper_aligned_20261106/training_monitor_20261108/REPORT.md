# 训练耗时、损失及 GPU 回收核对（2026-11-08）

本次只读原有记录，并在内存副本上完成一次 CPU 前向／反向计时；没有执行优化器更新、新增 SCIP 求解或修改冻结训练包。用户最新决定为保持现有训练配置，不实施设备迁移、调度改造或短时限评测。

## 论文、作者代码与当前实现的边界

- [论文 §4.3](https://arxiv.org/html/2511.12986v1#S4.SS3)规定 25 实例 × solver seeds 0–4、500 个完整 episode；每个 episode 到证明完成或 3600 秒上限。
- [论文 §5.3](https://arxiv.org/html/2511.12986v1#S5.SS3)规定每个完整 episode 后三轮优化、AdamW，并明确写实验运行在 40 核 CPU 节点。正文没有报告 GPU 型号、CPU 采样／GPU 更新分工或完成 500 episode 的总墙时。
- 已在线复核[作者公开 train.py](https://github.com/benmhamed-a/tgppo-aaai-26/blob/main/code/train.py#L104)：`build_agent_env_with_models` 固定 `get_device(device="cpu")`；采样 worker 与中央 learner 都使用这个构建函数。因此该公开训练入口的采样与优化均走 CPU，不能说作者采用了“CPU 采样＋GPU 更新”。在线文件 blob SHA 为 `ba392589fe0e08592e2122f2585fbb4ea77dcb3a`，与本地入口的相关内容一致。
- 当前 CPU 采样与 CPU 原生归一化有源码／实际记录支持；CUDA PPO learner 是本项目的工程设备选择，不是论文明确要求。作者公开入口还实现了多进程批量采样后更新，与论文正文逐 episode 更新的描述并不逐项相同；当前方案按已确认的正文逐完整 episode 更新执行。不能将公开入口默认并行数或 40 核节点直接换算成当前任务的加速比。
- 当前累计 48 小时来自此前用户确认的资源预算，论文未规定这个总训练上限。到预算时若尚未 500，需按实际进度报告，不能当作完整 500 实验。

“采样前间隔”含原生归一化、本进程等共享缓存锁及部分 I/O，现有记录无法将这些项精确分离；不能把这一列全部算成求解或全部算成阻塞。表格不含尚在运行的 episode、初始化及部分导入／保存开销。

258 个前缀采样结果的 `cuda_initialized` 全为 false。当前约 7%–10% 的上述阶段墙时用于 PPO 更新；这不是 GPU SM 利用率测量，更新内也包含 CPU 工作，此外初始化／检查／BC 也可能使用 GPU。没有连续 nvidia-smi 采样，不能给出准确 GPU 活跃占比。

11:48 北京时间快照的进度为 seed11 B0=86、MLP=87、MLP＋BC=87；seed22 B0=42、MLP=47、MLP＋BC=52。数字只代表当时共享记录，不代替平台进程状态。104/125 对原生归一化已缓存；它们的总 worker 墙时约 14.09 小时，并非每组都重复支付同等求解成本。

## 损失趋势

以下为每 20 个 episode 中非空更新的 Critic loss 算术均值：

| seed=11 方法 | 1–20 | 21–40 | 41–60 | 61–80 |
|---|---:|---:|---:|---:|
| B0 | 28.37 | 19.06 | 21.38 | 24.63 |
| MLP | 27.27 | 18.48 | 21.49 | 26.81 |
| MLP＋BC | 24.49 | 13.14 | 17.57 | 22.29 |

已确认事实：没有持续单调下降，三组均先降后波动／回升；已完成记录未发现 NaN／Inf。Actor loss 也不是持续下降曲线。详见 `metrics.csv`、`loss_windows.csv`。

源码机制：Actor 优势每次更新重新标准化，Critic 的回报目标来自每个新 episode；实例、solver seed、状态分布和策略都会变化。因此上述均值不能证明收敛、训练退化或测试收益。BC 较低的 Critic loss 也不能单独证明求解质量优越。缺少固定求解面板上的中途评价；当前遵从原固定 500 主对照，不在本轮添加评测。

## seed22 两次释放的直接证据

| 事件（北京时间） | MLP，第48个 episode | MLP＋BC，第53个 episode |
|---|---|---|
| 上一完整更新提交 | 03:44:27 | 05:49:49 |
| 下一 CPU 采样开始 | 04:44:29 | 06:49:52 |
| 完整轨迹／pending 保存 | 05:44:55 | 07:49:55 |
| 收到 SIGTERM | 05:45:03 | 07:50:03 |

两例均为 `rmatr200-p5`，solver seeds 分别 1、2。原生分母由对应训练主机自己补测，worker 耗时均约 3600 秒；随后 CPU 采样又各耗时约 3600 秒。保存 pending 后约 8 秒、已进入 PPO 更新时收到 SIGTERM。直接日志证明外部信号中断，并未报告 OOM／非有限损失。结合用户提供的平台解释，长时间 GPU 闲置导致资源回收是与记录一致的原因；具体平台阈值／判定采样窗口没有日志证据，不能声称已核实。

这不是 seed22 的模型必然不稳定：该 seed 的实例顺序使两次长归一化＋长采样相邻出现。seed11 也可能出现 GPU 长空闲，没有免疫保证。重新提交 `--resume` 可以恢复算法状态，但不改变平台回收机制。

## 独立 CPU 计时的限度

`CPU_TIMING.json` 记录了 27.93 秒总墙时、单线程、CUDA 未初始化。仅复用已保存的 1295 个状态中的少量输入，候选数范围 27–66，测试前／反向传播，没有 optimizer.step 或保存权重。B0 Actor 为按同架构初始化的计时副本；不是新 B0 训练，也不是整轮 CPU PPO benchmark。

这里的 55 秒脚本截止／60 秒外层保护只限制这一次独立诊断，未改变训练的 3600 秒 SCIP 上限、500 episode、更新规则或 48 小时累计资源预算。冷启动与少量候选规模不能用于可靠外推整个 500 episode 的 CPU 训练时间，也不能据此声称切 CPU 更快。

本次保持原训练协议，未启动新增评测。论文没有给出总训练墙时，因此也不能声称目前进度比作者慢多少；日志支持的结论是当前主要等待来自 CPU 求解／归一化，而常驻 GPU 的调度方式与平台回收规则不匹配。
