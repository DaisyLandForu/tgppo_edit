# 完整 Actor、在线 pilot 与开发求解验证

日期：2026-11-02 启动。依据用户“你把剩下的直接都验证完吧”的连续授权，执行本地 CPU 有界验证。

**核心结论：更新、加载和部署链路检查通过；8维尾部改动仍只有微弱、来源依赖的在线响应，没有观察到稳定的实际求解收益，也没有一致的纯前向加速。当前不能把 `8→1` 当作已验证有效的修复，不建议据此扩大正式训练或接入 HSTU。**

已完成70项真实SCIP任务和80次optimizer更新。两个来源的PDI变化方向相反，证明率均未提高；16/40项评估未触发Actor。H3分量审计量化了饱和现象，但尚未证明它对性能的因果影响。本轮是缩预算诊断，不是原论文完整性能复现。

## 1. 范围与公平性

原头与 tail8 × 两个来源种子11/22；头初值固定为101，没有按已测结果选最好初始化。上游与 Critic 取相同来源 ep100 权重，配对评分头从先前已保存 initial.pt 载入，最终标量读出归零，两头均使用 fresh Adam。保留前五层与完整树门控，仅替换尾部 8→4→2→1 为 8→1。原基线与历史结果未改。

这是一套统一初始化的暖启动对照，不能当作原 B0 的原样续训。离线桥接使用完整同版本缓冲的原 GAE，在原固定256条 batch上重复两次完整Actor/Critic更新。在线各组只做4个20秒完整episode采样和一个有界PPO块：8个256条逻辑batch，批内无放回、批间复用全缓冲，完整缓冲GAE，n_epochs=1。该更新计划是双方共用的缩预算pilot，并非历史3个完整epoch。奖励公式、学习率、clip、gamma/lambda均未改。

训练仅用 neos20/rmatr100-p10 × solver seeds0/1；开发用既定全部5实例 × solver seeds0/1。配对组使用与组名无关的动作RNG种子；评估只加载Actor。原生基线在同机同20秒、同cutoff和求解设置下重测，不能混用历史120秒归一化。

## 6. 结论边界与剩余证据缺口

E1：本轮已验证完整Actor更新、梯度、checkpoint/Actor-only加载、真实采样、开发求解、CPU成本与奖励分量；实例与来源方向详见上表。头部学习响应与真实求解收益是两个结论，不能用TV变化代替PDI证据。

E3：仍没有完整候选行动价值/专家排序真值，真实求解只能提供任务级证据；没有证明每个所选动作更优。一个短采样-更新块也不能检验长期收敛；两个来源模型、五个曾使用的开发实例不足以宣称广泛泛化。没有使用66测试集，也没有把已查看测试数据重新包装成未见集合。

本轮不再追加宽度搜索、初始化搜索、奖励替换或完整训练。是否扩大正式实验应依据实测的来源一致性、逐实例收益和成本决定；若仅有离线响应而无稳定任务收益，保留负结果，优先审计奖励/上游表示，而不是直接加入HSTU。

| 问题 | 本轮最终判断 |
|---|---|
| 是否只是更新没执行、模型没加载或部署仍调用Critic | **E1：受控检查通过，未发现这些问题。** 不替代所有历史运行的审计 |
| 尾部改动是否已恢复有效端到端学习 | **E1：只有微弱响应。** 两来源在线TV约1.5e-6/1.7e-7，不能等同正确分支偏好 |
| 是否得到稳定求解增益 | **E1：未观察到。** 来源方向相反、证明率同为40%，Actor参与的3实例上仍方向相反 |
| 是否降低部署成本 | **E1：无一致加速证据。** 固定状态纯forward约15.6–16.3ms，原主要计算路径仍在 |
| H3是否就是性能不佳的唯一根因 | **E3：未验证。** 饱和、节点项负向饱和与PDI项符号已测，不是奖励变体的因果对照 |
| 原方法长期训练是否必然无效、能否严格泛化 | **E3：本轮无法回答。** 仅一个短更新块和现有5开发实例；本轮改头方案在120秒协议下的收益、更长训练与真正独立测试仍未检验 |

后续若继续投入，应先选“上游候选信息是否足够”或“优势/奖励是否服务任务目标”中的一个问题单独验证；当前数据不支持继续把尾部宽度搜索或复杂模型作为优先路线。候选级正确性需要可追溯标签，长期收益需要有辨识力的同预算长训练/求解，均不能由本次微小概率变化补足。

## 7. 完整性与预算

共完成70个SCIP任务（14原生、16采样、40开发），80个optimizer.step（离线16、在线64），CUDA初始化0，原源码与历史输入356项哈希保持一致。所有开发任务valid，Critic评估用时为0；更新后的候选排列/追加masked padding检查通过。

全局单线程计算实耗 **3439.79秒（57.33分钟）**；加封存预留30秒保守计 **3469.79秒 <3600秒**，最终台账见 [budget.json](budget.json)。按实测完整网络吞吐，将pilot局部上限从1400秒改为2400秒；全局上限、训练步数和求解数量不变。监护进程交接时暂停并保留原训练worker，再由新监护恢复；没有重跑任何optimizer步或求解，记录见 [交接记录](pilot_supervisor_handoff.json)。
